# ADR-0012: Phase 3 设计定稿 —— 偏好确认语义、会话摘要机制与种子脚本

- **状态**:已接受
- **日期**:2026-08-06
- **决策者**:Kai(经 grill 会话确认)
- **细化**:ADR-0008 的 Phase 3 范围(「体验打磨」口袋)、ADR-0009 的「待确认草稿」语义、ADR-0010 的「会话摘要」机制

## 背景 (Context)

Phase 2 已交付(持久化会话、tool-loop、pantry/收藏写工具、操作卡片 undo)。Phase 3 的范围早在 ADR-0008 锁定(偏好写入确认卡片、滑窗+会话摘要、长会话种子脚本、体验打磨),验收场景 E1–E4 / F1–F3 也已写死,但设计层有六个未定的岔路。经 grill 会话逐一拷问后定稿,本文记录其中满足 ADR 三标准(难反转、无上下文会惊讶、真实权衡)的决策。

** grill 过程中的关键代码实证**:

- 现有写工具仅 `add_pantry_items` / `remove_pantry_items` / `set_favorite`,`update_preferences` 尚不存在。
- `PreferenceService.upsert` 支持部分字段更新,前端 `updatePreferences` / `usePreferences`(乐观更新 + 失败回滚)已存在——确认路径无需新 API。
- **A4「刷新后撤销只读」边界当前无机制支撑**:`ChatActionCard` 的 `undone` 是 `useState`,刷新后撤销按钮复活,且撤销基于 tool output 里的过期 pantry 快照计算(可能冲掉之后新增的食材)。确认卡片要沿用同一边界,必须先建立「历史消息只读」机制,两类卡片共用。

## 决策 (Decision)

### 1. Phase 3 范围澄清:「体验打磨」限缩

ADR-0008 的 Phase 3 第四项「体验打磨」限缩为**实现 E/F 过程中直接长出的打磨**(确认卡片样式、摘要相关交互等),不预先罗列独立打磨项;无关灵感记 backlog,不占 Phase 3 范围。**Phase 3 完成判定 = 验收清单 E1–E4 + F1–F3 全过**。

### 2. 刷新后确认卡片只读

偏好确认卡片与操作卡片(A4)共用同一边界:**刷新前可操作,刷新后可渲染但操作只读**,过期确认卡片引导用户重新发起(如「该草稿已过期,请再告诉我一次」)。

- 不为「已确认/已取消」状态持久化开口子——消息 parts 落库后不可变(ADR-0011 重审后的干净状态),确认状态只活在当前页面会话内。
- 连带要求:实现「历史消息只读」机制(区分流式新消息与历史拉取消息),操作卡片的撤销边界一并补齐(修背景中发现的 A4 机制缺口)。

### 3. 草稿 = 操作集,确认时合并

`update_preferences` 工具**结构上不落库**,只产出「待确认草稿」作为 tool output(随消息 parts 持久化)。草稿内容是**操作集**而非目标快照:

- `addDisliked` / `removeDisliked` / `addAllergens` / `removeAllergens` / `setHealthGoal`(按需出现)。
- 确认 = 前端读当前偏好 → apply 操作集(add 并集、remove 差集、healthGoal 覆盖)→ 调现有 `PUT /preferences`。不引入新端点、不引入基线版本号。
- E4 红线(「你看着办,直接改吧」不得绕过确认)由架构保证:工具没有落库能力,确认只认前端按钮,不依赖 prompt 自觉。
- 过敏原**移除**操作在卡片 diff 上以警告色强调(实现层要求)。

### 4. 会话摘要:异步 + 增量 + 两列存储

- **触发**:每轮响应落库后(`ChatService` 的 `onFinish` 钩子内)检查:未覆盖的溢出消息(seq ≤ maxSeq − 滑窗大小,且 seq 大于 `summaryUpToSeq`)攒够阈值 → 后台起摘要任务。用户请求路径零延迟;阈值为实现常量,以代码为准。
- **更新策略**:增量——新摘要 = 压缩(旧摘要 + 新溢出消息)。不做全量重算。
- **存储**:`Conversation` 表加 `summary`(文本)与 `summaryUpToSeq`(整数)两列,不新建表。
- **注入**:`buildSystemPrompt` 加「会话摘要」段落,与现有偏好/pantry 注入同构;滑窗逻辑不变。
- **失败处理**:摘要 LLM 调用失败 → 记录日志、保持旧摘要,下轮响应后自然重试。降级形态 = 现状(纯滑窗)。

### 5. 种子脚本:插库 + 直调摘要服务

验收 F2/F3 的前置:脚本(`apps/server/scripts/`,tsx 运行)直接插库构造 40+ 条消息的会话(text parts),随后**进程内直调摘要 service 函数**预生成摘要——不走 HTTP、不烧 20+ 轮真实对话。走查时第一条探测消息即达完整形态(滑窗 + 摘要)。

## 理由 (Rationale)

- **范围限缩**:「体验打磨」无验收场景对应,装进去的东西没有完成标准,Phase 3 的「完成」将不可判定;摘要机制本身已是「实现最微妙」项,范围越大交付越晚。
- **刷新只读**:与 A4 边界一致,用户只需学一条规则「卡片操作只在当前页面会话内有效」;重发一句话成本极低;避免为确认状态引入「修改已落库消息」的新机制。
- **操作集草稿**:自然语言表达的本是增量操作(「我不吃香菜」= add);目标快照在并行修改下会静默冲掉数据——若被冲掉的是过敏原,E1–E4 守住了「未确认不落库」却守不住「确认时丢数据」,安全味不可接受。乐观锁对本项目(单用户、低频)收益不抵新接口语义成本。
- **异步摘要**:同步方案让跨阈值的那一轮突然多等一次完整 LLM 调用,违背「没有慢到想关掉」的体感验收原则;异步的失败降级形态恰好是现状,天然安全。
- **增量摘要**:摘要机制存在的理由是「成本有界」;全量重算的输入随会话长度线性增长,自我违背。「摘要的摘要」漂移风险在菜谱推荐域(话题短而浅)可忽略,验收也只要求话题连续。
- **种子脚本直调 service**:纯插库造不出摘要(摘要挂在真实对话的 `onFinish` 上),走查需先发热身消息,步骤别扭;真实 API 回放慢、烧 token、不可重复(探测点写不死)。

## 备选方案 (Alternatives Considered)

- **草稿 = 目标快照,确认全量覆盖**:实现最简,但并行修改被静默覆盖(见理由),否。
- **草稿带基线 + 乐观锁 409**:最严谨,需新接口语义与「过期重发起」流程,单用户场景收益低,否。
- **刷新后仍可确认**:技术上可行(草稿在 parts、确认是前端直调),但「已确认」状态刷新后丢失,卡片会对已生效草稿继续显示「待确认」,UI 撒谎,否。
- **同步(请求时)摘要**:摘要始终最新,但跨阈值轮次延迟突增,否。
- **全量重算摘要**:质量更稳但成本无界,否。
- **种子走真实 API 回放**:消息形状全真且顺带压测触发链路,但慢、烧 token、不可重复,否。

## 后果 (Consequences)

- 正面:E4 红线由架构(工具无落库能力)而非 prompt 自觉保证;确认语义对并行修改鲁棒;摘要用户路径零延迟、成本有界、失败降级为现状;F2 走查可确定重复。
- 负面:`Conversation` 表一次迁移(加两列);前端需新建「历史消息只读」机制(顺带补 A4 缺口);增量摘要的理论漂移由验收标准(话题连续即可)兜住。
- Future Work:backlog 中的独立打磨项;若未来引入「原子轮次」(ADR-0011 Future Work),摘要触发点可从 `onFinish` 迁移到轮次提交处。
