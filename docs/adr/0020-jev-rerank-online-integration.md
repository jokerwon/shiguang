# ADR-0020: Jev 候选重排序接入线上搜索（候选池上限 + 模型生成软偏好 + 分阶段放量）

- **状态**：已接受（接入设计定稿；线上收益尚未验证，放量按门槛分阶段）
- **日期**：2026-10-09
- **Phase**：11
- **决策者**：Kai
- **关系**：消费 [Phase 10](../implementation/phase-10-implementation.md) 的离线实验结论（`continue`，净胜 13），不改动其场景、快照与结论。不改 [ADR-0005](./0005-personalized-recommendation.md) 的排序权重、[ADR-0017](./0017-remove-pantry-and-shopping-list.md) 的纯偏好排序、[ADR-0018](./0018-ingredient-catalog-and-filtering.md) 的安全边界与 [ADR-0019](./0019-recipe-ingredient-single-source.md) 的原料单一事实源。本 ADR 有意放宽 Phase 10「线上链路零改动」的实验隔离约束——接入即改动线上，故必须先有此决策。
- **勘误（2026-10-09，同日）**：初稿的容量模型自相矛盾（池上限 12 + 串行派发 + 1500ms 超时三者不相容，会让几乎每次搜索都超时回退），且把实验场景的候选数（4–19）误当作线上候选池规模。决策 2/4/5/8 与后果已按真实代码与实测数据修正，改动见文末[勘误记录](#勘误记录2026-10-09)。本 ADR 同日发布、尚未实施，故直接修正原文而非新开 ADR。

## 背景 (Context)

Phase 10 离线实验对「完整合格候选」重排后，用户 30 场景盲评净胜 13（门槛 6），出口 `continue`＝建议继续接入设计。决策时点对真实代码核对的事实如下。

### 线上链路与三个形态缺口

- 线上 `search_recipes` 的返回是 `restrictRanked(ranked, filtered).slice(0, input.limit ?? 6)`（`src/chat/tools/read-tools-logic.ts:244`）：候选池 `restrictRanked(ranked, filtered)` 是**全部合格候选**（基线顺序），`slice` 只取前 `limit`；工具 schema 的 `limit` 上限为 **12**（`src/chat/tools/read-tools.ts:48-53`）。
- **缺口一（候选池规模）**：`let filtered = recipes`（`read-tools-logic.ts:139`），关键词/食材/菜系/标签/营养**全部可选**，因此**无参查询时候选池 = 全库**（当前 88 道，随内容增长），而非实验场景实测的 4–19 道（那是「都带 cuisine/maxTime 等硬条件」的结果）。池上限因此是**承重设计**，必须按全库规模考虑并写明未封顶的最坏情形。
- **缺口二（收益是否存活）**：按已入库 `results.json` 复核，**Jev top4 平均只有 2.13/4 落在基线 top6 内**——若线上只重排 `slice` 后的 6 道，Jev 只能在固定 6 道内换序，约一半以上收益来源被截断。
- **缺口三（软偏好来源）**：实验的 `soft.primary/secondary`（如「省事、步骤少、烹饪时间短」）是**人工固定**的（`src/experiment/scenarios.ts:47`）。线上 `buildSystemPrompt` 注入的动态上下文只有用户名、忌口/过敏、健康目标、季节与会话摘要（`src/chat/prompts/context-builder.ts:12-23`），**没有软偏好字段**；`search_recipes` 的入参只有结构化筛选条件。软偏好只存在于用户消息文本里，由聊天模型理解——**线上必须由模型生成，其质量未经盲评验证**。

### 调用模型与容量事实

- 实验协议：**1 候选 = 1 请求**（31/31 场景请求数等于候选数），脚本**串行**发送并主动限流：`minIntervalMs = ceil(60000 / rpm)`，`--rpm` 默认 90 → 667ms/次（`scripts/experiment.ts:237,317-319`）。
- 账号级限速 **100 RPM**（实测 429），即平均 600ms 才允许一次请求。均摊 1133 输入 / 78 输出 token；单次实测 p50 439ms、p95 605ms、最大 20.9s（离群，触发过重试）。
- 结论：**限速是吞吐硬顶，不是延迟硬顶**。N 个候选若**并行**派发，单次搜索的墙钟延迟约等于一轮往返（≈0.6–0.9s），但会消耗 N/90 分钟的速率预算 → 吞吐上限 = 90/N 次搜索/分钟。若**串行**派发，12 个候选需要 ≥7.2s，任何秒级超时都会失败。因此派发方式必须在决策中写死，不能留给实现。
- `@typesafe-ai/sdk@0.6.0` 当前在 `devDependencies`；Jev 调用与不变量检查在 `src/experiment/jev.ts`，仅被离线脚本消费，不参与线上构建。

### 既有约束

- 安全过滤与硬条件由代码先于模型执行，模型不得恢复被排除候选（ADR-0018 安全红线、Phase 10 不变量）。
- 线上为流式 tool-loop：`chat.service` → `createChatTools` → `search_recipes.execute` → `runSearchRecipes`（`streamText` + `toUIMessageStream`）；重排发生在工具内，会计入模型可见的工具结果与整体响应时延。
- 线上 `findRecipes()` 返回完整 Prisma `Recipe` + `ingredientLinks`（`chat.service.ts:210-225`），已含 `desc`/`steps`/营养/原料——**足以构造与实验同一份 `RecipeFactView`，无需补写资料**。
- 服务端对第三方调用已有「如实报错、不静默降级为错误结果」的习惯；本 ADR 的回退是**回到基线排序**（正确结果），不是伪造结果。

## 决策 (Decision)

### 1. 接入位置与语义

- 在 `runSearchRecipes` 内部、`rankRecipes` 之后、`slice` 之前对**候选池**重排：`restrictRanked(ranked, filtered)` → Jev 重排 → `slice(0, limit)`。
- 重排**只改顺序**：不增删候选、不改变 `count`/`note`/`error`/`ingredients` 语义、不参与安全过滤、不改变 `rankRecipes` 的权重与轮换种子（`rankRecipes` 本身不改，共享排序保持单一事实源）。
- 重排的输入顺序即 `rankRecipes` 的输出顺序（基线顺序），用于同分与不可评价候选的稳定回退。
- 注入点复用既有 seam：`ChatToolDeps` 增可选 `rerank` 客户端；离线评估与线上接入共用同一实现。

### 2. 候选池上限（承重参数）

- 新增 `JEV_RERANK_MAX_CANDIDATES`（默认 **12**，与工具 `limit` 上限一致）：仅对候选池**前 N 道**送模型重排，其余候选保持基线相对顺序追加在后。
- 该上限同时是**成本与吞吐的主控**：单次搜索的模型调用数 = `min(候选池, N)`，池可达全库（88+），因此**未封顶的最坏情形是 N 次调用**，这一点由上限保证，不依赖池大小。
- 调整上限必须同时复核决策 5 的吞吐与超时模型，不能单独调。

### 3. 软偏好来源

- 扩 `search_recipes` 的 `inputSchema`，新增**可选** `demand`：`{ primary: string; secondary?: string }`，由聊天模型按用户原话填写（主/次偏好及优先级），与实验 `soft` 字段语义一致。
- 工具描述明确：**填不出或用户未表达偏好就不要填**，宁可不重排也不猜。
- `demand` 缺失、为空或字段非法 → 本次不重排，返回基线顺序（不报错、不提示）。

### 4. 协议与派发（两者分开）

- **协议保持** Phase 10 已验证的**单候选、并列两问**（资料充分性 Choice + 四级匹配 Score）：一次请求只含一个候选，避免候选间比较干扰。只有「资料足够」才消费 Score；「资料不足」「无法确定」后置但保留；同分沿用基线顺序。
- **派发改为并行**：同一次搜索内的 N 个候选请求**并发发出**，并发上限 = N，并由一个**全局令牌桶**（补充速率 90/分钟，容量 = N）统一限流。并行**不改变**请求内容与协议，只改变调度——因此不使 Phase 10 的证据失效。
- 不允许串行派发：串行 + 账号限速会让 N=12 至少耗时 7.2s，任何秒级超时都必然失败。

### 5. 降级、超时与开关（一组自洽默认值）

| 参数 | 默认 | 依据 |
|---|---|---|
| `JEV_RERANK_MODE` | `off` | `off`/`shadow`/`live`；`off` 时 `runSearchRecipes` 返回与当前**逐字节一致** |
| `JEV_RERANK_MODEL` | 无默认（启用时必填） | 代理路由名与官方版本名不同（如路由 `g-jev-1.13` 响应 `jev-1.13.0`），硬编码任何一个都会在另一套环境静默失败 |
| `JEV_RERANK_MAX_CANDIDATES` | 12 | 与 `limit` 上限一致；决定吞吐与单次调用数 |
| `JEV_RERANK_TIMEOUT_MS` | 2000 | 覆盖并行派发下一轮往返（p95 605ms）的 3 倍余量 |
| `JEV_RERANK_ROLLOUT_PERCENT` | 0 | `live` 模式下的生效比例 |
| `JEV_RERANK_RPM` | 90 | 令牌桶补充速率（容量 = N），低于账号上限 100 |

- 超时预算是**单次搜索的墙钟预算**，覆盖并行派发与重试；**不覆盖**令牌桶排队——桶内令牌不足时**立即放弃**本次重排（回退基线），不排队等待，避免把限速变成用户可见延迟。
- 吞吐上限 = 90 / N 次搜索/分钟（N=12 → 7.5 次/分钟）。超过即回退基线，属预期行为，不是故障。
- 其他降级条件：异常、未配置凭证、预算超限、SDK 错误、`demand` 缺失——一律回退基线顺序，不抛错、不阻塞工具、不向用户暴露失败。
- 实测中单次请求出现过 20.9s 离群值；此类请求会在预算内被放弃并回退基线，属可接受行为。

### 6. 数据边界

- 只发送：菜谱事实（名称/简介/菜系/标签/时长/营养/原料/步骤）与模型生成的 `demand` 文本。
- **不发送**：用户标识、原始聊天消息全文、偏好档案原文（忌口/过敏/健康目标）。
- `demand` 由模型概括，不含姓名、联系方式或用户未在本次需求中表达的个人信息。

### 7. 依赖方向

- `@typesafe-ai/sdk` 从 `devDependencies` 移到 `dependencies`（生产依赖，随部署安装；Node ≥20 已是项目要求）。
- 把 Jev 调用、问题构造、`rerank`、事实视图与 `checkRerankInvariants` 从 `src/experiment/` 提取为生产模块 `src/recipe/jev-rerank/`，**离线评估与线上接入复用同一模块**，不允许第二套实现。`src/experiment/` 继续只做场景、快照与评估统计。

### 8. 放量与可观测性

- 三阶段放量，按用户 id 稳定分桶：
  1. **影子**：计算重排并记录「基线前 6 vs 重排前 6」差异，**返回基线顺序**。
  2. **灰度**：按 `JEV_RERANK_ROLLOUT_PERCENT` 生效。
  3. **全量**：比例 100。
- **影子的代价必须写清**：影子在工具内**同步**执行，因此**付出与生效路径相同的延迟（最多 `JEV_RERANK_TIMEOUT_MS`）与相同费用**，只是丢弃排序结果。决策 5 中「关闭时逐字节一致」指的是**内容与顺序**，不包含延迟；影子不是「零成本观测」。
- 每次搜索记录：候选池大小、实际调用数、重排耗时（墙钟）、是否生效、降级原因、失败数；影子阶段额外记录两组前 6 的差异。

## 理由 (Rationale)

- 在候选池（而非 `slice` 后）重排，是唯一能让实验收益在线上存活的位置；把上限做成旋钮而非硬编码，是因为「收益 vs 调用量」在线上形态下尚未量化。
- 保持**单候选协议** = 保持 Phase 10 全部证据有效；只把**调度**改为并行，是因为限速是速率而非并发约束，并行把 7.2s 的串行墙钟压回一轮往返，且不改请求内容。
- 默认关闭 + 超时回退 + 基线回退 + 令牌桶不足即放弃，使第三方可用性、限速与费用问题**不影响**线上正确性：最坏情况退化为当前行为（延迟除外，故影子代价单列）。
- 依赖方向明确（提取生产模块而非复制），避免实验与线上两套 Jev 实现分叉——这是 Phase 9 单事实源教训的同类应用。

## 备选方案 (Alternatives Considered)

- **只重排线上 `slice` 后的 top6**：改动最小、调用最少（6 次），但已复核约一半以上收益来源被截断；拒绝作为唯一形态，改为候选池上限可调。
- **串行派发 + 秒级超时**：初稿的组合，实测不相容（12 候选 ≥7.2s）；拒绝。
- **排队等待令牌桶**：会把账号限速直接变成用户可见延迟，且延迟不可预测；拒绝，改为不足即回退。
- **批量提问（一次评 K 个候选）**：调用数可降为 1/K、吞吐显著提升，但引入候选间比较干扰，Phase 10 协议结论不成立，需重做一轮盲评；本轮不采用，保留为后续选项。
- **影子改为返回后异步 fire-and-forget**：可省延迟，但记录可能在进程退出时丢失、且难以与请求上下文关联；本轮不采用，改为同步影子并写明代价。
- **把软偏好塞进 `rankRecipes` 的现有权重**：现有权重只表达时间/营养/健康目标，无法表达「省事」「下饭」这类文本偏好；拒绝。
- **不接入，仅保留离线实验**：开关默认关闭即等价于该选项，作为随时可退的兜底保留。

## 后果 (Consequences)

- **线上收益未经盲评验证**（候选池 ≤12 + 模型生成 `demand`，与实验形态不同），因此**不得直接全量**；必须按下列事先固定的门槛放量：
  - **影子阶段**：≥200 次真实搜索、降级率 <5%、重排墙钟 p95 <1.5s（并行派发下可达；串行派发下达不到）、0 次因重排导致的工具错误。
  - **灰度阶段**：用户盲评或点击对比净胜 >0，且无安全/硬条件回归。
  - 门槛不满足 → 停在影子或关闭开关。
- **吞吐与成本**：吞吐上限 90/12 = **7.5 次搜索/分钟**，超出即回退基线；单次搜索 ≤12 次调用；估算每千次搜索（12 候选）≈ US$0.6（估算，非账单，价格与计费条件未核实）。
- **延迟**：生效路径与影子路径都会给工具结果增加最多 `JEV_RERANK_TIMEOUT_MS`（默认 2s）的等待；该「延迟 vs 收益」的权衡**未经验证**，须由影子阶段的实测延迟分布与灰度收益共同判定。
- **新增第三方可用性依赖**：已用超时 + 基线回退 + 默认关闭隔离，线上正确性不依赖其可用性。
- `@typesafe-ai/sdk` 进入生产依赖，部署需安装。
- 若日后改批量协议，本 ADR 的单候选协议结论作废，必须重跑盲评。
- 文档同步：`docs/README.md` 索引、`docs/glossary.md` 术语、`docs/implementation/phase-11-implementation.md` 实施清单与对应验收清单。

## 未验证项（接入前必须显式承认）

1. **线上收益**：候选池 ≤12 + 模型生成 `demand` 下的净胜未知，Phase 10 的「全量候选 + 人工软偏好」结论不可直接等同。
2. **呈现层**：`search_recipes` 的返回会交给聊天模型（`chat.service` 的流式 tool-loop），由模型决定如何复述、取舍与排列——**Jev 的排序偏好是否等价于用户最终所见，未经验证**。实验测的是原始候选顺序偏好，不是用户实际看到的呈现顺序。
3. **延迟与收益的权衡**：新增最多 2s 的工具等待是否值得，未经验证。
4. **成本与计费**：账号价格与最低充值条件未核实，费用均为估算。
5. **「本次需求」一段的来源不同**（离线 vs 线上唯一不一致处）：离线实验传 `brief.request` = 人工固定的原始需求原文，state 里渲染为「本次需求（人工固定，未经模型提取）：「…」」；线上没有、也不得发送聊天原文，只有模型自己概括的 `demand`，渲染为「本次需求（由对话模型按用户原话概括，未经人工核对）：」，模型填不出 `demand` 时整段不重排。事实视图、问题、评分口径、单候选协议均逐字相同。**Phase 10 的净胜 13 是在「原始需求原文」下测得的**，线上效果还取决于聊天模型概括 `demand` 的准确度；概括偏差会让 Jev 按错误偏好排序。

| # | 初稿 | 问题 | 修正 |
|---|------|------|------|
| 1 | 「候选池 4–19 道（均值 13.4）」作为容量依据 | 那是**实验场景**（都带硬条件）的实测值；线上无参查询池 = 全库（`read-tools-logic.ts:139`），当前 88 且随内容增长 | 决策 2 改为按全库规模陈述，明确上限承重、最坏情形 N 次调用 |
