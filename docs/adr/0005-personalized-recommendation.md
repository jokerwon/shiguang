# ADR-0005: 个性化推荐 —— 服务端 `/recipes/personalized`,偏好三维 + 隐式信号加权

- **状态**:已接受
- **日期**:2026-07-29
- **决策者**:Kai(经 grill 会话确认)

## 背景 (Context)

个性化主题下需落地「偏好档案 + 个性化首页」。但存在两个关键待定项:

1. **推荐算法归属**:现有 `matchScore` / `matchRecipes` 是**前端**函数,在浏览器拿菜谱数组 + localStorage pantry 现算。数据迁服务端后,算法放哪决定接口形状。
2. **首页排序信号**:不能只做"pantry 匹配",否则与食材页同质化,个性化无差异化价值。

偏好档案维度也需克制——每加一个维度,用户多填一项、算法多处理一个信号。

## 决策 (Decision)

**推荐算法收口服务端**:新增 `GET /recipes/personalized`,后端读当前用户 pantry + 偏好,过滤 + 排序后返回成品列表。前端 `matchScore` 仅保留给食材页本地即时反馈(pantry 未同步时)。

**推荐流程**:
1. **硬过滤**:排除含忌口食材、过敏原的菜谱。
2. **加权排序**:pantry 匹配度 + 时间适配 + 新鲜度轮换。

**排序信号**:
- **pantry 匹配度**:主料重叠度(复用匹配逻辑,服务端实现)。
- **时间适配**:按当前时段推导(如晚间优先 ≤30min),无需用户配置。
- **新鲜度轮换**:无状态,以 `userId + 当天日期` 为随机种子,按天轮换、当天内稳定。**不新增 impressions 表**。

**偏好档案维度:忌口食材 + 过敏原 + 健康目标(均衡/减脂/增肌)**。健康目标映射到营养三要素排序(减脂→低卡低碳优先,增肌→高蛋白优先)。**不采集**饮食类型、偏好菜系。

**偏好入口:设置页 + 首页软提示。** 空档案时首页降级为现有行为(pantry + 时间 + 轮换,无忌口过滤),并在首页放非阻断软提示"完善偏好,让推荐更准"。

## 理由 (Rationale)

- 服务端算:推荐逻辑单一事实源,一个接口同时喂首页与 AI 注入,避免前端一套、AI 一套。
- 时间适配 + 新鲜度轮换是**不依赖用户主动配置**的隐式信号,让首页有"不配置也智能"的差异化。
- 无状态轮换:100 道菜的库,"未见过"收益小且需新表,日期种子足够,零存储。
- 偏好三维都能精确映射到可计算字段;菜系自述噪声大,留待行为推断。

## 备选方案 (Alternatives Considered)

- **客户端算**:逻辑散在前端,AI 注入需重复实现,且要拉全量菜谱,否。
- **分层(硬过滤服务端 + 排序客户端)**:逻辑撕裂两处维护,否。
- **基于"未见过"的新鲜度(新 impressions 表)**:需持续写入 + 新表,违背 Phase 2 不新增存储的收敛,否。
- **强制 Onboarding 采集偏好**:新流程 + 分步 UI 工作量大,会撑爆版本,否。
- **采集饮食类型 / 偏好菜系**:饮食类型用 VEGETARIAN tag 兜住;菜系自述不准,否。

## 后果 (Consequences)

- 正面:推荐有据可依、千人千面;隐式信号降低配置门槛;逻辑收口后端。
- 负面:需写后端推荐算法 + 传用户态;`TODAY_NAMES` 硬编码被移除;空档案体验需设计降级。
- 影响:`/recipes/recommended` 的 `today` 逻辑被 `/recipes/personalized` 取代或重构。
